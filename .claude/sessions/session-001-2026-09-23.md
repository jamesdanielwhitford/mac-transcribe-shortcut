# Session 001 - 2026-09-23

## What this session covered

Debugged an intermittent bug in `tts-clipboard.py`: for long clipboard text
(multi-chunk, 3+ chunks), QuickTime Player would sometimes fail to open the
generated MP3 with "The document ... could not be opened. The file isn't
compatible with QuickTime Player." Reopening the same file manually afterward
usually worked.

## Investigation

Found two live copies of the script running as separate LaunchAgents, plus a
third copy in this git repo that was already stale before this session:
- `~/CODE/voice-transcribe/tts-clipboard.py` - the one actually running (`com.tts-clipboard` LaunchAgent)
- `~/Documents/CODE/voice-transcribe/tts-clipboard.py` - this repo, was out of sync

Added `[debug]` logging at each stage (chunk synthesis byte counts, ffmpeg
concat output, file existence/size checks, `open` return codes) and set
`PYTHONUNBUFFERED=1` in the LaunchAgent plist so log lines weren't stuck in
Python's stdout buffer.

Ruled out, in order, using ffprobe/ffmpeg decode checks on both a failing
file and a working one:
- File corruption / incomplete write - decode was always clean, no ffmpeg errors.
- Timing race (file not settled before `open` fires) - added a settle-wait
  loop, still failed.
- `ffmpeg -f concat` demuxer producing bad duration headers - switched to
  the `concat` audio filter (decode+reencode), still failed with the same
  symptom.
- Anomalous duration/probe_score - the ~10 minute duration for a ~10,000
  character article was actually correct math (~150 wpm), and the same low
  `probe_score=51` appeared on a small file that had already been confirmed
  to open fine, so it wasn't diagnostic of anything.

The actual root cause: `subprocess.Popen(["open", "-a", "QuickTime Player", path])`
(and even the synchronous `subprocess.run` version) only confirms Launch
Services accepted the request to launch/activate the app - it returns success
even when QuickTime itself later fails to parse the file. The file content
was never actually the problem in the cases we caught; the open handoff was
the point of failure and gave no error signal back to the script.

## Fix

- Multi-chunk audio path switched from generating separate MP3s per chunk
  and stitching them with ffmpeg, to requesting raw LINEAR16 PCM per chunk,
  concatenating the raw PCM byte-for-byte (no container ambiguity), and
  doing a single clean ffmpeg encode to MP3 at the end.
- Replaced the `open -a` fire-and-forget call with a `play_audio()` function
  that opens the file in QuickTime via AppleScript (`tell application
  "QuickTime Player" to open POSIX file ...`) and verifies success by
  checking QuickTime's document count actually increased. If that isn't
  confirmed, it falls back to playing the audio directly with `afplay` and
  notifies the user, so audio is guaranteed either way even if QuickTime's
  GUI is misbehaving.
- Removed the `[debug]` print statements and empty-audio warnings added
  during troubleshooting before committing - kept the PCM fsync and the
  file-size-before-playback guard since those are real correctness checks,
  not debug noise.
- Synced the fix into both the live running copy (`~/CODE/voice-transcribe/`)
  and this repo (`~/Documents/CODE/voice-transcribe/`), which had drifted
  apart before this session.

## Verification

Multiple back-to-back triggers of the same 3-chunk long-text case after the
`play_audio()` fix all showed `doc_count before=0 after=1` (confirmed
successful QuickTime open, no afplay fallback needed) and the user confirmed
audio played correctly. Did not manage to force a failure under the new code
path in the time available, so this is "seems fixed, keep watching" rather
than a fully reproduced-then-fixed confirmation, since the original bug was
intermittent, not 100% reproducible.

## Part 2: URL-to-speech feature, and removing the afplay fallback

Added a feature to `tts-clipboard.py`: when the clipboard holds a URL and
nothing else, the tool now fetches the page's article content and speaks
that instead of reading the raw URL string aloud. Built via three
sequential subagents (plan, build, test), per this user's standing
orchestration preference.

### What was built

- `is_url_only(text)` - detects clipboard content that is a single URL
  (must start with `http://`/`https://`/`www.`, no internal whitespace) and
  nothing else. A URL followed by other text, or on its own line among
  other lines, is correctly treated as ordinary text, not a URL.
- `extract_article_text(url)` - shells out to a new `extract_url_text.py`
  script via `uv run` (absolute path `/opt/homebrew/bin/uv`, since the
  LaunchAgent's PATH doesn't include Homebrew - same reason `ffmpeg` is
  already invoked by absolute path in this file), 45s timeout. Raises
  `RuntimeError` on any failure (non-zero exit, timeout, unparsable
  output).
- `extract_url_text.py` (new file) - reuses
  `~/.claude/skills/better-research/scripts/research_lib.py`'s
  `fetch_page()` (requests-first, Playwright-fallback, readability-based
  extraction with several guard heuristics already built into that shared
  library) rather than writing a second, weaker scraper. Prints
  `title\n\n{article text}` to stdout.
- In `speak_clipboard()`: if `is_url_only()`, notify "Fetching article...",
  call `extract_article_text()`, and on success replace `text` with
  `"{title}. {article_text}"` before falling through into the existing
  chunking/synthesis/playback pipeline unchanged. On any extraction
  failure, notify with the error and fall back to speaking the literal URL
  string rather than hard-stopping - mirrors the existing
  fallback-with-notification pattern already used for QuickTime playback
  failures.
- Fixed a pre-existing latent bug in `notify()`: it interpolated the
  message directly into an AppleScript string literal with zero escaping.
  This would have broken routinely once article titles (which often
  contain `"` or apostrophes) started flowing through it. Now escapes `\`
  and `"` before interpolating.

### Verified end-to-end

A real `speak_clipboard()` run against
`https://htmx.org/essays/markdown-in-src/` produced a genuine extracted
article ("</> htmx ~ Markdown in /src", 8240 chars) spoken in full (2
chunks), not the URL read aloud. Confirmed via the testing subagent, which
also verified: URL+text and multi-line clipboard content correctly
fall through to normal behavior (regression-safe), a 404/unreachable URL
fails cleanly within the timeout (no hang) and falls back to speaking the
literal URL, and the `notify()` escaping fix works on a message containing
both `"` and `\`.

### Playwright browser binary mismatch (found during testing, fixed after)

The testing subagent found that `research_lib.py`'s Playwright fallback
path was broken: the browser binary cached under
`~/Library/Caches/ms-playwright/` didn't match what the currently-resolved
`uv run` environment expected (version 1243 needed, only 1228/1234
present) - a pre-existing issue in the shared `better-research` skill,
already logged in that skill's own `LEARNED.md`. This meant any URL
needing the Playwright-render fallback (JS-heavy pages) would fail
extraction and silently fall back to speaking the raw URL instead of the
article.

Fixed after testing confirmed it was the only real gap: running
`/opt/homebrew/bin/uv run --with playwright playwright install chromium`
from inside the `voice-transcribe` repo directory (so it resolves the same
ephemeral `uv` environment `extract_url_text.py` itself uses - this
matters, since running the same install command from the
`better-research` skill's own directory resolves a *different* env/cache
key and does not fix the one this feature actually depends on). Verified
fixed afterward against `https://react.dev/learn` (a JS-rendered docs
page), which now extracts full clean article text via the Playwright path
instead of failing.

### Removed the afplay fallback in play_audio()

After the URL feature was live, a real trigger hit the QuickTime-open
verification failure path, which fell back to `afplay` - a headless
command-line player with no window and no pause/stop control. The user
had audio playing on their laptop with no way to control it short of
finding and killing the process manually, and said this should never
happen. Removed the `afplay` fallback entirely: if QuickTime can't be
confirmed to have opened the file, `play_audio()` now just notifies
("QuickTime couldn't open the file - it's saved on your Desktop") and
stops. The MP3 is always saved to Desktop regardless, so nothing is lost -
the user can open it manually if this happens. No code path in this file
plays audio without QuickTime's controls anymore.
